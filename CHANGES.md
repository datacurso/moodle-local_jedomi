# Changes

## Unreleased (1.7.0)

- Add `\local_jedomi\public_api::chat_available(int $userid, \context $context)`: other plugins ask whether the Jedomi chat is offered to a user in a context (active user who is not a guest, Jedomi enabled in the Datacurso AI provider, the course available to Jedomi and a role not hidden from it) before they show something that opens it
- Add the AMD module `local_jedomi/api` for other plugins: `isAvailable()` tells whether the panel is on the page, and `openWithSuggestion(prompt)` (or `{prompt, source}`) opens the panel with the text written in the message field, as plain text the user can change and send. It is never sent on its own; a suggestion is cut to 4000 characters and waits up to 15 seconds for a panel that is still loading
- Add the hook `\local_jedomi\hook\tool_registry`: other plugins give Jedomi their own tools from their `db/hooks.php`. The web chat dispatches it with the user, the signed course (or the system) and the channel, offers a tool only when its plugin's `is_available($userid, $context)` answers true, runs it as the session user, logs it as a Jedomi tool and anonymises its result like any other. A tool without `is_available()`, with a malformed name, with the name of a Jedomi tool or of an earlier plugin tool, or whose definition names another tool is ignored; a failing tool answers a controlled error, and a result over 100 KB is replaced by a `tool_result_too_large` error. A tool declares with `is_read_only()` whether it only reads: a tool that changes something, or does not declare it, waits for the user's confirmation card (severity high) and runs only when confirmed, as the user and only if its plugin still offers it in the context it was held in. Telegram and the scheduled agents do not offer plugin tools yet
- Fixed: the instructions of the web chat, Telegram and the scheduled agents carry the date of today (`- Today: 2026-11-18 (Wednesday), time zone America/Bogota`), taken from the server clock in the time zone of the user and never from the request, with a rule to read relative dates ("last month", "since ...") against it. Before, the AI did not know the date and compared periods of earlier years when asked about "last month"
- Added: plugin tools whose data is still being prepared are asked again. A read-only plugin tool that answers a JSON object with `"meta": {"pending": true}` at its top level (the contract of the `tool_registry` hook; the course tools of `local_datacurso_heatmap` answer so) is run again with the same arguments after 10 seconds, at most 3 runs within 25 seconds and 30 seconds of waiting in all for one turn (`\local_jedomi\local\plugin_tool_retry`), and the AI gets the last answer. A tool that changes data, an answer with `error`, a failing tool or any other shape (a text, `"pending": "true"`, `pending` outside `meta`) is never run again. If the data is still being prepared after the last run, the instructions tell the AI to say that it will be ready in about a minute, never that there is no data. Each new run is logged (`PLUGIN_TOOL_PENDING_RETRY`)
- Security (RISK-001): the parameters of a web service write of a scheduled agent are validated as Moodle validates them before the scope is checked, and the write is held or run with exactly those validated parameters: an identifier written as a float or a boolean (such as `99.0`, `1.0` or `true`, which Moodle turns into integers) can no longer slip past the scope. A write whose parameters Moodle rejects returns the validation error and is neither run nor held. Any parameter named like an identifier (ending in `id` or `ids`) that is not a known target makes the write held, whatever its type
- Security (JEDOMI-SEC-014): every approved write of a scheduled agent has its arguments checked against the context of the agent, also for site agents. A write that names nothing concrete of the site (no target at all, or only the top level of the categories, the system context or the front page: its course, context, activities and groups), or whose targets cannot be resolved, is no longer treated as inside the scope: it is held for the creator instead of running. An injected "create a category" read by a site agent with that function approved is now held (RE-POC-2c). Every element of every collection, at any depth and whatever its keys (lists, object-keyed collections, lists nested in a record, wrapper objects), is a record that needs a concrete target among its own fields inside the scope, also when it is empty or has no scalar field, so a valid record cannot carry an injected one; a record anchored only by an ancestor, an empty record or a record without a target field makes the write held. Writes with a concrete target inside the scope still run without confirmation (a site agent covers the whole site, so a category under an existing category runs). Site-agent writes whose only targets are user attributes such as a new `username` or `email` (creating or updating users) are now held for confirmation (REL-004)
- Security (RISK-001): recipients given by `username`, by `email`, as `{type, value}` (`usertype`, `cohorttype` of `core_cohort_add_cohort_members`) or as the members of a cohort (`cohortid`, `cohortids`, by id or idnumber) are resolved to users, checked against the scope of the agent and counted toward the cap of 50 recipients per run; a user or cohort that cannot be resolved makes the write unverifiable, so it is held. Parameters named like recipients (`users`, `userlist`, `recipients`, `members`, `participants`, `touser`, `tousers`, `to`) are user ids when they hold ids; any other value in them makes the write held (RISK-002). Only the members needed to reach the recipient cap (51 or 52) are read from a cohort, so a large cohort stops the run at the cap without a lookup per member (RES-004)
- Security (RISK-003): only the creator of an agent approves the writes it held, and only while the agent still exists and belongs to them; a site administrator may cancel them but not approve them on behalf of the creator (there is no delegation). Only the owner of an agent adds approved writes to it: a manager or administrator editing the agent of someone else may keep or remove them, and an agent given to another owner starts without approved writes unless the new owner approves them. Approved writes added by a non-owner before this version are kept (REL-005)
- Fixed (RES-003): a retry of a failed scheduled run no longer repeats the approved writes that the failed attempts already made successfully. Each write is recorded on the agent (`local_jedomi_agents.runwrites`: fingerprint of the function and its normalised parameters, outcome and recipients) before it runs and until a run succeeds. In the retry a write that succeeded is skipped and the AI is told it was already made; a write that failed cleanly runs again; a write whose outcome is unknown (it threw, or the run died while it ran) is held for the creator. The writes of the failed attempts count toward the caps of the retry. The fingerprint is taken from the validated parameters with their keys sorted, so an id written as text or as a number is the same write, while texts that differ only in white space, or "007" and "7" in an idnumber, are different writes (a cohort given by idnumber and by id still gives two fingerprints). Editing the instruction, schedule or approved writes of an agent, or enabling it again, clears these writes; if they are unreadable, every write of the run is held (REL-002)
- Fixed (RES-006): an approved write that reaches execution counts toward the cap of the run even when it throws after being applied, and is reported as failed
- Security (JEDOMI-SEC-002): the web chat no longer writes free text sent by the browser in the system message. The title of the page is dropped (the panel no longer sends it), the name of the course is read on the server from the signed course when the user can enter it (dropped otherwise), the activity name and type come from the activity the user can see, and the page address keeps only a plain path (letters, digits and `/._-~`; anything else is dropped)
- Security (JEDOMI-SEC-005, SEC-JD-006/007/008/009/012): tool results in the web chat and Telegram, the text of attached files (web chat through `extract_file.php` and Telegram), what the vision model read from an image or a scanned PDF, and the names of the course and activity of the page (web chat, agents) and of the courses of the user (Telegram) reach the AI between the untrusted data markers already used by the agents (`\local_jedomi\local\untrusted`). The rule that content between the markers is data, never instructions, is now in the instructions of every channel, and names files, images and Moodle names. The name of an attached file or image goes inside its block too (RISK-001). The panel sends only the wrapped text returned by `extract_file.php` (`untrusted_text`) and shows an error when it is missing (RES-001). The anonymiser keeps the markers with their random id, also at the Strict level, and still anonymises and restores the content between them (REL-001). Markers the AI echoes are removed from the answer shown in the web chat and Telegram (REL-003)
- Security (SEC-JD-013/014/111): the instructions of the web chat, the agents and Telegram forbid revealing them, and carry only the major Moodle version (such as `4.5`) instead of the full release and build. The site instructions of the Personalization tab no longer sit between `SITE INSTRUCTIONS` markers that a text could close: they come in a "SITE PREFERENCES (lower priority)" section that says they cannot override the rules above, with each line quoted with `> `
- Fixed (REL-008): an agent preview answered from its cache sends the fresh tool results of the replayed plan as untrusted data, with the rule about them
- Upgrade (2026111900): new field `local_jedomi_agents.runwrites`
- Tests: browser page texts never in the system message and server-resolved course and activity names; untrusted markers on tool results (web chat, Telegram, preview cache replay), document and image texts; major version, no-disclosure rule and quoted site preferences; scope of site agents without a concrete target, recipients by username, email and cohort, the RE-POC-2c regression in a full run, approval of held writes by someone other than the creator (service and web service), approved writes added by a non-owner, retries that skip only successful writes, rerun clean failures and hold writes of unknown outcome, corrupt run writes, the fingerprint normalisation, clearing on edit and re-enable, injected elements in a list of records, recipient-like parameters and large cohorts, failed writes counted toward the cap

## 1.6.3 (2026-11-17)

- Changed: the custom AI service mirrors the Datacurso fields. Once the connection is verified only the chat model is shown as a model field; image processing, documents, audio processing and the voice conversation each have their own switch (`custom_files_enabled`, `custom_documents_enabled`, `custom_audio_enabled`, `custom_voice_enabled`), and their fields (image model, document service URL, audio model, voice model and voice) are shown, and required, only while the switch is on. The voice conversation still needs audio processing. The custom service has its own switches instead of sharing the Datacurso ones, so each service keeps its own settings and switching services never turns a feature of the other one on or off. At runtime a feature of the custom service is on only while its switch is on and its model is set; a model behind a switch that is off is kept for later when it is a valid id
- Changed: the custom max tokens start on the default (16384), on a new form, when nothing is saved and right after a verification of an empty field, instead of empty
- Added: documents with the custom service. A new "Document service URL" (`custom_docservice_url`), shown under the "Documents" switch and required while it is on, points to a PDF-to-images service (`POST {url}/api/v1/pdf/to-images?dpi=150&fmt=JPEG`, the contract of the former document service). PDF files attached in the web chat, sent in Telegram or read by `document_read` are turned into page images and each page (at most 20, chosen after the `pages` asked, so `document_read` can read pages after the 20th) is read by the custom image model; documents need image processing. The whole read has one deadline, the AI request timeout: the document service and each page get the time left, and the pages left when it runs out are skipped. A page the image model fails on is skipped and the others are kept (a timeout or a lost connection stops the read, as it would repeat); the read fails only when no page was read, and each page is logged (`VISION_PAGE`: number, duration, outcome). Pages asked that are not in the document give a clear message. The page count told by the service is capped at 10,000, and the skipped pages are listed up to 100 with their full count (`pages_skipped_total`). The address follows the policy of the custom service URL (HTTPS, HTTP only for a local host with "Allow HTTP for local models", cURL security, no redirects, pinned local address), with a 5 s connection timeout, a 120 s total timeout and caps on the PDF (20 MB), the answer (32 MB, enforced while it arrives) and each image (10 MB); errors never carry the address or the answer. Text files (`.txt`, `.csv`, `.md`, up to 2 MB, cut at 200,000 characters) are read on the site, also only with "Documents" on and the document service URL; Word and PowerPoint files are refused with a message asking for a PDF. With the switch off or no address, documents are refused as before. The Datacurso service is unchanged
- Added: context window of the custom service (`custom_context_window`). "Verify connection" returns the context length of each model when the service tells it (`max_model_len` of vLLM, `context_length`, `context_window`, `max_context_length`) in `contextlengths` of `local_jedomi_verify_custom_service`, keeps them (`custom_context_lengths`), and the page shows the one of the chosen chat model as the placeholder ("16384 (auto)"); a typed value overrides it, and the max tokens must be smaller than the window. While a window is known, the default max tokens of the custom service (form, saved empty value, runtime and the page after a verification) is half the window, at most 16384, and the trimming never reserves more than half the window for the answer (logged once as `CONTEXT_RESERVE_CLAMPED`), so a max tokens as large as the window never drops the whole history. Before each AI request of the web chat with the custom service, the tokens are estimated (four characters per token) and the oldest history that does not fit next to the max tokens and the tools is dropped: never the system message or the latest user turn, never an assistant tool call without its results, and the kept history starts with a user message. Each trimming is logged (`CONTEXT_TRIMMED`, counts only). Empty and nothing detected means no trimming
- Added: "AI request timeout (seconds)" (`ai_timeout`, 10 to 600, default 180), shared by both services and shown after their fields, used by every AI request without a timeout of its own (web chat, CLI); Telegram and the scheduled agents keep theirs. Its help warns that proxies (Cloudflare closes at 100 s), `max_execution_time` of PHP and the web server can end a request earlier
- Added: "Maximum rows per query (web chat)" (`sql_row_limit_web`, 10 to 1000, default 100) in the General tab; the AI is told the limit. Telegram, the companion web service and the agents keep their fixed limits
- Privacy: the PDF files sent to the document service of the custom service are declared (`jedomi_custom_document_service`), and the files sent to the custom service now include the page images of PDF files
- Upgrade (2026111800): each custom switch starts on when its model was saved (voice: model and voice), so a configured site keeps its features; documents start off; an empty custom max tokens becomes 16384; `ai_timeout` (180) and `sql_row_limit_web` (100) are saved when missing. Saved values and the Datacurso switches are never changed
- Tests: form visibility and validation of the custom switches, documents, context window, max tokens and timeout; defaults and upgrade step; the document service client with a fake transport (contract, timeouts, size caps, page cap, address policy, error privacy); PDF, text and Office files with the custom service; context length detection; the trimming algorithm and its use in the web chat; the timeout setting; the web row limit

## 1.6.2 (2026-11-17)

- Fixed: the service URL of the custom AI service is used as the provider documents it, with the convention of the `base_url` of the OpenAI SDK. A URL without a path (such as `http://localhost:11434` or `https://api.openai.com`) gets `/v1`; a URL with a path (such as `https://api.openai.com/v1`, `https://api.deepinfra.com/v1/openai`, `https://api.groq.com/openai/v1` or `https://openrouter.ai/api/v1`) is used as given, without trailing slashes, and each route (`/models`, `/chat/completions`, `/audio/transcriptions`, `/audio/speech`) is added to it. Before, `/v1` was always added after removing a trailing `/v1`, so DeepInfra (`https://api.deepinfra.com/v1/openai`) was called at `/v1/openai/v1/models` and answered 404. A URL with a query, a fragment or credentials is still refused
- The URL is saved as the root of its API (`custom_endpoint::normalise()`), so the field shows `/v1` after a URL without a path, and the verification fingerprint (`custom_verified`) is taken from that root: a host and the same host with `/v1` are the same service, a path with and without `/v1` are two services
- The help of the "Service URL" field, its placeholder and the README describe the new rule
- Added: "Verify connection" shows the ids of the models the custom service lists and offers them as suggestions (one `datalist`) in the chat, image, audio and voice model fields, which stay free text. `local_jedomi_verify_custom_service` returns `models` (only ids the model fields accept, without repetitions, sorted, at most 100) and `modeltotal` (the number of those ids); the page says how many are shown when there are more. The ids, which come from the external service, are only set as text and DOM properties, never as HTML
- Upgrade (2026111700): the saved `custom_gateway_url`, kept without its `/v1` until now, gets it back, so a saved custom service keeps calling the same addresses; the verification of the saved address and key is kept with its original time, so nothing has to be verified again. A verification of an address and key that were not saved is dropped, also when no address is saved. The step records that it ran (`custom_url_rule_upgraded`), so it never adds `/v1` twice
- Tests: the root of the API and the address of every route for OpenAI, DeepInfra, Groq, OpenRouter, Ollama and a custom path, the fingerprint of equivalent addresses, and the upgrade of the saved URL and its verification

## 1.6.1 (2026-11-13)

- Security (JEDOMI-SEC-001): scheduled agents are safe and autonomous. The agent form has a new "Writes run without confirmation" list with the web service functions that change data from the web service list saved for the role of the owner; the approved functions are stored per agent (`local_jedomi_agents.approvedwrites`, a JSON list) and the details of an agent show them. An agent created by the chat, Telegram or another agent has none
- Security (JEDOMI-SEC-001): during a run (`write_guard`) a write runs without confirmation only when its function is approved for the agent and its arguments stay inside the fixed scope of the agent (`write_scope`), checked on the server: the course, category, user context or site of the agent, and as recipients only the creator and the users enrolled in its course or courses (the context user for a user agent; users enrolled in any course for a site agent). A target outside the scope is rejected; a write whose targets cannot be verified, any other write and every agent management or administration operation is held as a pending action of the creator (with the agent id, valid for 7 days instead of 15 minutes) to approve or reject in the Jedomi web chat. A cached plan replayed by a later run goes through the same guard, so a write in it never runs. Approval in Telegram is not offered yet, and the summary of the writes is a Moodle notification (popup and email by default), not a Telegram message
- Security (JEDOMI-SEC-001): each run makes at most 20 approved writes to at most 50 distinct recipients other than the creator (and holds at most 20 writes); going over stops the run, which counts as a failed run, so five such runs in a row disable the agent with the existing failure notice. Every automatic, held or rejected write is written to the technical log without its arguments, and the creator gets a Moodle notification (new message provider `agentwrites`) after each run with writes listing the writes run, waiting for approval and rejected
- Security (JEDOMI-SEC-001): in the scheduled run and the preview of an agent, tool results reach the AI between `<<<UNTRUSTED_DATA id=…>>>` and `<<<END_UNTRUSTED_DATA id=…>>>` markers with a random marker per run (markers inside the content are neutralised), and the agent instructions say that this content is data that must never be followed. The instructions no longer say that writes run immediately
- Security (JEDOMI-SEC-001): agents run no web service function while no web service list is saved for the role of their creator, also for administrators (the web chat and Telegram keep the full access of an administrator without a saved list)
- Security (JEDOMI-SEC-008): the web chat and the agent tool executor only run (or hold) tools offered to the role of the user, after resolving their alternative names (`create_agents`, `delete_agents`, `list_agent`, `call_webservice`); the agent tool executor runs nothing until the tools are prepared for a user, so no tool runs as user 0
- Fixed: the preview of an agent could run a web service write called through `call_webservice` with `function`; pending actions now classify every tool call by its canonical name and arguments (`pending_action_service::normalise()`)
- Upgrade (2026111304): existing agents have no approved writes, so all their writes wait for the approval of their creator, who is notified after each run; a notice in the Agents tab says so. Approve the writes each agent needs in its form after saving a web service list for the role of its owner
- Security (JEDOMI-SEC-002): the web chat accepts from the browser only user messages and assistant texts without tool calls, rebuilt with their role and content alone and limited to the latest 30; system, tool, assistant tool-call and malformed messages are dropped, so they never reach the AI. The channel and output of the system message are fixed by the server for the web chat, and `system_message` accepts only the channels `chat` and `agent` and the outputs `web` and `telegram`
- Security (JEDOMI-SEC-003): every table whose name starts with `local_jedomi_`, present or future, is sensitive for the SQL guard (Telegram sessions and pending actions, agents and their hidden instructions, agent cache, query log, feedback and web chat pending actions), for every user including administrators; the existing list of sensitive site tables is kept
- Security (JEDOMI-SEC-004): the Telegram webhook secret is sent by Telegram in the `X-Telegram-Bot-Api-Secret-Token` header (`setWebhook` with `secret_token`) and is no longer part of the webhook address; a secret in the query string is no longer accepted. The self-ping that continues long turns verifies TLS and sends the secret in the same header. Version 2026111303 rotates the secret and registers the webhook again when a bot token is configured; if Telegram cannot be reached, the Integrations tab shows a warning until the bot token is saved again
- Resilience (RES-001): the Telegram webhook is registered with `setWebhook` alone, which replaces the previous webhook at once, and is never deleted first (also when dropping the pending updates, which `setWebhook` now does itself), so a failed registration no longer leaves the bot without webhook. Every Telegram request gives up connecting after 5 seconds, and the upgrade waits at most 10 seconds for Telegram. The upgrade (2026111303) stores the new secret only once Telegram accepted it; when it fails, the webhook refuses every request (also with the old secret), a line is printed in the upgrade output, the Integrations tab warns, and the new adhoc task `register_telegram_webhook` retries the registration with a new secret for about 17 hours (11 attempts with the cron backoff), notifying the site administrators on the first and on the last failed attempt (new message provider `telegramwebhook`). Saving the bot token while the warning is shown registers a new secret
- Upgrade (2026111305): registers the message provider `telegramwebhook`; no data changes
- Security (RISK-I3): the details of an agent no longer give its last error to users who may not read its instruction (they see only that the last run failed, with the failure count), and a failed run stores a generic message with a reference instead of the raw exception message; AI errors and empty answers keep their translated messages, and the details stay in the technical log, anonymised
- Security (JEDOMI-SEC-012): the capabilities `local/jedomi:manageagents` (configuration, data loss, personal data and spam risks) and `local/jedomi:companion_api` (configuration, data loss and personal data risks) declare their risks
- Fixed: the average duration of the "Slowest queries (avg)" report of the Query profiler tab is red only at or above the slow query threshold, like the duration of the "Recent queries" report, instead of always
- Fixed: a replaced custom avatar is shown at once instead of the old image kept for a day by browsers and proxies: its address carries the moment of the image as its revision (in place of the item id), which `local_jedomi_pluginfile()` ignores, so older addresses still work
- The technical log of a failed request of the custom AI service (`AI_ERROR`, `SPEECH_ERROR`) keeps its HTTP status, cURL error number or refusal reason (`detail`), never the key or the answer; the user message is unchanged
- The ten preset avatars (`pix/avatars`) are 256 × 256 px transparent PNG images of 19 to 56 KB instead of 1024 × 1024 px images of up to 620 KB (about 0.33 MB in total instead of 3.6 MB)
- Tests: `ajax/agent_stats.php` counts only the agents that match the filters each user saved in the agents report, and never matches the hidden instruction of an agent in the prompt search of a manager

### Security

- The technical log (`jedomi.log`) no longer keeps Moodle user ids, Telegram chat ids or agent names: users and chats appear as pseudonyms (a keyed hash with a random key of the site), and the source IP address is kept only for requests rejected for security reasons. The log, its content and its size-based retention are declared in the privacy registry
- The database query guard reads the query as the database does: a new parser (`local\sql_select_parser`) checks every piece of a teacher's query against a small grammar (SELECT, FROM, INNER/LEFT JOIN with ON, WHERE with AND, comparisons, IN, IS NULL, LIKE, GROUP BY, ORDER BY, LIMIT, COUNT/SUM/AVG/MIN/MAX/ROUND/COALESCE) before the course filter. This closes ways a teacher could read data of courses they do not manage: hiding the course filter inside CASE, a backquoted reserved word as an alias, a control character after `--`, and a `?` inside a comment that shifted the query parameters. For every user, control characters, executable comments (`/*!`, `/*M!`, `/*+`) and placeholders that the database would bind differently are rejected, and on PostgreSQL, SQL Server and Oracle the quoting the guard cannot follow is rejected. Teachers lose OR, NOT, CASE, subqueries, HAVING, arithmetic and functions other than the listed aggregates
- Database queries of the web chat, Telegram, the companion service and the agents now really stop after their time limit (5 seconds; 30 seconds for agents): a `MAX_EXECUTION_TIME` hint on MySQL, `SET STATEMENT max_statement_time` on MariaDB and a restored `statement_timeout` on PostgreSQL, never a session-wide setting. The row limit is applied by the database (Moodle's limit, or the query's own LIMIT lowered to it) instead of after loading every row into memory. The agents' SQL tool now accepts only SELECT and WITH queries
- The voice conversation sends the text to be read aloud anonymised at the level of the Privacy tab: site user names and email addresses (and codes at the Strict level) are replaced by generic spoken words such as "a person" or "an email address" before the text leaves the site; the chat still shows the real answer. The privacy declaration of the speech service now lists the language, site id and site URL sent with each request
- The document reading tool (`document_read`) reads only the PDF the activity publishes (its description, attachments and content areas of the module), never student submissions, feedback, forum post attachments or quiz responses, and checks course access first, so a suspended or hidden-course enrolment is refused before any other permission
- Secret columns are recognised by name, not only from a fixed list: any column ending in secret, token, password, passwd, private key, API key, session key or salt (for example `consumersecret`, `refreshtoken`, `approval_token`, `guestpassword`) is rejected in queries and removed from rows, for every user; token counters and password flags that hold no secret stay readable.
